# 02 – Coding Standards

Version: 1.0

Author: Maria Fe Blanca

---

# Purpose

This document defines the coding standards for the AI Operations Platform (AIOP).

The objective is to ensure that all source code remains readable, maintainable, secure, testable, and scalable regardless of whether it is written by a human developer or generated by an AI coding assistant.

These standards apply to:

- Google Apps Script
- JavaScript
- Shared Libraries
- Integration Modules
- Future Backend Services

---

# Engineering Philosophy

Code should be:

Simple.

Readable.

Predictable.

Reusable.

Secure.

Documented.

Every module should be understandable without requiring extensive explanation.

Future developers should spend time extending the platform—not deciphering existing code.

---

# Core Principles

The platform follows these engineering principles:

- Single Responsibility Principle (SRP)
- Separation of Concerns
- DRY (Don't Repeat Yourself)
- KISS (Keep It Simple)
- Composition over Duplication
- Explicit over Implicit

---

# File Organization

Every file must have one responsibility.

Good

```
WorkflowEngine.gs

ClaudeService.gs

KnowledgeManager.gs

Logger.gs
```

Bad

```
Everything.gs

Utilities2.gs

FinalScript.gs
```

---

# Maximum File Size

Recommended

300–500 lines

Maximum

800 lines

If a file exceeds 800 lines, evaluate splitting it into smaller modules.

---

# Function Standards

Functions should:

- Perform one task
- Be reusable
- Return predictable values
- Avoid side effects where possible

---

Good

```javascript
function classifyEmail(email) {}
```

Bad

```javascript
function processEverything() {}
```

---

# Function Length

Recommended

20–40 lines

Maximum

80 lines

Longer functions should be refactored.

---

# Function Naming

Use camelCase.

Examples

```
loadKnowledge()

generatePrompt()

callClaude()

createDocument()

sendNotification()
```

Functions should begin with verbs.

---

# Variables

Use descriptive camelCase names.

Good

```
residentEmail

workflowStatus

knowledgeContext
```

Bad

```
a

temp

data2

obj
```

---

# Constants

Use

UPPER_SNAKE_CASE

Examples

```
MAX_RETRY_COUNT

API_TIMEOUT

DEFAULT_MODEL
```

---

# Magic Values

Never hardcode values.

Bad

```javascript
Utilities.sleep(5000);
```

Good

```javascript
Utilities.sleep(DEFAULT_RETRY_DELAY);
```

---

# Configuration

Store configuration externally.

Never hardcode:

API keys

URLs

Company IDs

Secrets

Feature flags

Use:

Script Properties

Configuration Manager

Environment Variables

---

# Error Handling

Every external operation should use try/catch.

Example

```javascript
try {

    const response = callClaude(prompt);

} catch (error) {

    Logger.error(error);

    throw error;

}
```

Errors should never be silently ignored.

---

# Logging

Every workflow should log:

Workflow

Module

Execution time

Status

Errors

Prompt Version

Token Usage

Logs should be structured.

---

# Comments

Write comments that explain *why*, not *what*.

Bad

```javascript
// Increment counter
counter++;
```

Good

```javascript
// Prevent duplicate workflow execution
counter++;
```

---

# Documentation

Every public function should include documentation.

Example

```javascript
/**
 * Generates an AI prompt for resident emails.
 *
 * @param {Object} email
 * @return {String}
 */
```

---

# Return Values

Always return predictable objects.

Preferred

```javascript
return {

    success: true,

    data: response

};
```

Avoid mixed return types.

---

# Async Operations

Where supported:

- Avoid blocking operations
- Minimize API calls
- Batch requests
- Retry transient failures

---

# Dependency Management

Modules should communicate through interfaces.

Avoid direct coupling.

Good

```
WorkflowEngine

↓

ClaudeService

↓

IntegrationManager
```

Bad

```
WorkflowEngine

↓

Everything
```

---

# Business Logic

Business rules belong in:

Workflow Engine

Never inside:

Prompt files

Utilities

Logger

Configuration

---

# Utilities

Utility functions should:

- Be generic
- Be reusable
- Have no business knowledge

Good examples

Date formatting

String cleaning

Validation

Parsing

---

# AI Code Standards

AI-generated code must:

Be reviewed by humans.

Follow naming standards.

Follow security standards.

Pass testing.

Include documentation.

AI-generated code is never merged without review.

---

# Performance

Prefer:

Caching

Batch updates

Minimal API requests

Reusable services

Avoid:

Repeated API calls

Duplicate queries

Unnecessary loops

---

# Security

Never expose:

API Keys

Passwords

Secrets

PII

Always validate:

Inputs

Outputs

External responses

---

# Module Responsibilities

Each module has one purpose.

WorkflowEngine

Coordinates workflows

ClaudeService

Communicates with Claude

KnowledgeManager

Retrieves knowledge

PromptManager

Builds prompts

Logger

Captures audit logs

IntegrationManager

Communicates with external systems

---

# Code Review Checklist

Before merging:

☐ Naming follows standards

☐ Functions are small

☐ Modules have one responsibility

☐ Errors handled

☐ Logging added

☐ Documentation written

☐ Tests completed

☐ No duplicated logic

☐ Configuration externalized

☐ Security reviewed

---

# Anti-Patterns

Avoid:

God Classes

Massive Functions

Copy-Paste Programming

Hardcoded Configuration

Silent Errors

Deep Nesting

Global Variables

Business Logic in Utilities

Prompt Logic inside Workflows

---

# Definition of Clean Code

Clean code should:

Explain itself.

Require minimal comments.

Be easy to test.

Be easy to extend.

Be easy to review.

Remain understandable six months later.

---

# Coding Philosophy

Every line of code should answer one question:

> **Does this make the platform easier to understand, extend, and maintain?**

If the answer is no, reconsider the implementation.

The AI Operations Platform values long-term maintainability over short-term convenience.

Code is not just written for machines.

It is written for people.
